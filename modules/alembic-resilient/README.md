# Resilient Alembic module

Use this module when a project uses Alembic and may encounter databases whose schema was partially created, manually changed or restored from another environment.

## Principle

Alembic revision history remains the primary source of migration order. Each risky DDL operation may additionally inspect the live schema and choose one of three outcomes:

- `APPLIED`: the expected object did not exist and the migration created it.
- `SKIPPED_EQUAL`: the object already existed with an equivalent definition.
- `CONFLICT`: the object existed but its definition differed; abort instead of silently accepting drift.

Never skip merely because an object has the same name. Compare the relevant definition first.

## Included utility

Copy `templates/schema_guard.py` to `backend/app/db/migrations/schema_guard.py` or the equivalent project path and import it from revision files.

The helper supports guarded tables, columns and indexes and emits structured log markers.

## Example

```python
from alembic import op
import sqlalchemy as sa

from app.db.migrations.schema_guard import ensure_column


def upgrade() -> None:
    ensure_column(
        op,
        table_name="users",
        column=sa.Column("display_name", sa.String(length=120), nullable=True),
    )
```

## Rules

1. Inspect through `sqlalchemy.inspect(op.get_bind())`.
2. Apply when absent.
3. Skip only when equivalent.
4. Raise `SchemaConflictError` when present but different.
5. Log every decision with revision, operation, object and status.
6. Keep downgrade explicit; do not automatically delete pre-existing objects that the upgrade skipped.
7. Review autogenerated revisions before committing.
8. Prefer constraints and indexes with explicit stable names.
